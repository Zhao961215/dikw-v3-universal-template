## 一、一句话说清楚

**大脑存高频，图书馆存低频。** 这里的大脑是 Hermes 官方 Holographic 插件——使用 HRR（Holographic Reduced Representations）代数 + FTS5 全文索引进行双引擎检索，全本地运行，零网络依赖。

| 哪儿 | 叫什么 | 用来存什么 | 访问方式 |
|------|--------|-----------|---------|
| 🧠 **大脑** | Holographic 🛠️ `fact_store` / `fact_feedback` | 方法论、原则、红线，需要跨 session 持久化的内容 | `fact_store` 工具检索 / 写入 |
| 📚 **图书馆** | 知识库 Vault（`vault/`） | 偶尔翻阅的参考文档 | `read_file`，稍慢 |
| 🗂️ **卡片柜** | 实体页 Entities（`vault/entities/`） | 实体/概念的卡片信息 | `read_file` 直接读 |
| 📦 **仓库** | Data Cache（`data/{模块}/cache/`） | 原始数据、临时缓存 | 不直接访问，需要时抓取 |
| 🏃 **速查** | `session_search` | 近期对话历史 | 搜跨 session 上下文 |

## 二、Holographic 是什么——检索机制详解

### 能力一览

| 项目 | 说明 |
|------|------|
| 存储 | ✅ `fact_store` — 保存事实到 SQLite（自动创建 FTS5 全文索引 + HRR 向量） |
| 检索 | ✅ **双重机制**：每轮轮次前自动 FTS5 检索 + `fact_store` HRR probe 显式查询 |
| 反馈 | ✅ `fact_feedback` — 给事实打分（`action='helpful'` / `action='unhelpful'`） |
| 去重 | ✅ 自动去重，根据内容 UNIQUE 约束合并 |
| 持久化 | ✅ **跨 session 全局共享**到 `{工作区}/memory_store.db` |

### 跨 session 全局共享

Holographic 的 `memory_store.db` 是所有 session 共享的单库，**不按 session_id 做数据隔离**：

- `add_fact()` 写入时不关联 session_id
- `search()` / `probe()` 检索时不过滤 session_id
- session A 存的原则，session B 的 `prefetch`（自动 FTS5）和显式 `fact_store(query=...)`（HRR probe）都可以命中

**这意味着**：
1. ✅ **不需要固定 session ID**
2. ✅ 跨 session 记忆开箱即用
3. ⚠️ 存了不相关/低质量的事实会影响所有 session 的检索质量——确保 `query` 编码准确、`fact_feedback` 及时校准

### 检索机制：FTS5 + HRR 双引擎

```
  自动层（每轮注入）：FTS5 全文索引
  ─────────────────────────────────
  Hermes 内核在每次轮次前自动调用 prefetch()，
  用 FTS5 关键词匹配事实库，将相关事实注入上下文。
  所以即使你不显式调用 fact_store，模型也能感知到相关记忆。

  显式层Ａ（关键词检索）：FTS5 search_facts
  ─────────────────────────────────
  fact_store(action='search') 时，同时走 FTS5 关键词命中 +
  Jaccard 相似度重排 + trust 加权。

  显式层Ｂ（代数检索）：HRR probe
  ─────────────────────────────────
  fact_store(action='probe') 时，通过循环卷积计算实体与
  事实库之间的代数相关性，找到结构上相关的记忆。
```

### 检索流水线细节

```
fact_store(query="关键词")
  ↓
① FTS5 候选（limit × 3）：全文索引命中
  ↓
② Jaccard 重排：查询与事实内容的词元重叠度
  ↓
③ HRR 代数相似度：编码文本 → 循环卷积比对
  ↓
④ 加权融合：score = FTS5×0.4 + Jaccard×0.3 + HRR×0.3
  ↓
⑤ 信任加权：final = score × trust_score
  ↓
⑥ 返回 top-N
```

权重默认值：FTS5=0.4, Jaccard=0.3, HRR=0.3。可配置（见「配置调优」章节）。

### 不需要语义搜索的原因

HRR + FTS5 + Jaccard 的组合已经覆盖了 **80% 以上的检索场景**：

- FTS5 自动注入让你不需要每次都显式搜索
- Jaccard 重排弥补 FTS5 词序敏感的短板
- HRR 代数比纯关键词更灵活（对词序不敏感、支持部分匹配）
- 唯一覆盖不到的是**字面完全不重叠但语义相近**的查询——这通过正确编码关键词（见「HRR 关键词编码策略」）就能大幅缓解

**这对应的是设计取舍，不是缺陷**：在轻量设备上，加入语义搜索意味着引入深度学习模型（bge-m3 / Ollama），额外 1-2GB 内存 + CPU 负载。HRR 用纯代数运算替代语义模型，0 额外开销，不会因为 embedding 模型挂掉导致整个记忆系统瘫痪。

## 三、核心触发时刻——分析完成后自动分流

> **这是整套系统的真正触发点**，不是等用户说"存一下"才动手。

**每次完成一项分析/工作后——无论是讨论一个业务逻辑、debug 一个系统问题、还是梳理一个知识框架——自动执行以下操作：**

1. **归纳总结**：这次分析中使用了什么方法、逻辑框架、判断依据？把"怎么做的"提炼出来
2. **DIKW 分流**：将过程中产生的信息按四层模型分别处理（见下表）
3. **不需要问用户"要不要存"**——方法论直接进大脑，这是你的职责

### 具体实操：分析完成后自问三句

```
① 这次分析用了什么方法/框架？→ 存大脑（fact_store）
② 过程中产生了什么结构化数据？→ 存 entities/（write_file）
③ 有没有完整的分析报告？→ 存 vault/（write_file）
```

## 四、DIKW 四层模型——判断信息该放哪

```
┌─────────────────────────────────────┐
│         WISDOM（智慧）                │
│  不变的原则、框架、方法论              │
│  → 图书馆（完整版）+ 大脑（索引摘要）   │
├─────────────────────────────────────┤
│         KNOWLEDGE（知识）             │
│  实体信息、行业定义、概念解释            │
│  → 实体页（entities/）                │
├─────────────────────────────────────┤
│       INFORMATION（信息）              │
│  业务指标、快照数据——会变的动态数据      │
│  → Data Cache（带时间戳，30天失效）    │
├─────────────────────────────────────┤
│          DATA（数据）                  │
│  原始 API 返回、未处理的缓存            │
│  → Data/Cache 目录（临时）             │
└─────────────────────────────────────┘
```

**核心判断工具——问三个问题：**

| 问题 | 答案决定存哪 |
|------|-------------|
| 这个信息会变吗？ | **会变** → data cache（带时间戳） / **不会变** → 大脑或图书馆 |
| 我每次推理都要用吗？ | **高频** → 大脑（Holographic） / **偶尔查** → 图书馆（Vault） |
| 它是一张卡片还是一本书？ | **卡片**（单个实体）→ 实体页 / **体系化知识** → 图书馆 |

> ⚠️ 常见错误：把动态数据（快照、指标）塞进大脑。正确做法：动态数据进 data cache，大脑只存**不变的方法论**。
> ⚠️ Holographic HRR 检索天然对短文本更友好。长文本存前先提炼成**一句话原则**再存。

## 五、信息来了怎么办——三步分流

### Step 1：判断信息类型

```
信息进来
  │
  ├── 原始数据（未处理的API返回、日志）─────→ Data 临时目录
  │
  ├── 动态数据（指标/快照/短期判断）───────→ Data Cache（带时间戳）
```

### Step 2：检查是否已有同类信息

→ 有 → 更新/覆盖，不重复创建
→ 无 → 新建

### Step 3：执行存储

- data cache：`write_file` 到对应模块的 `data/` 目录
- 大脑（Holographic）：`fact_store`（方法论文档的索引摘要）
- entities：`write_file` 到 `vault/entities/` 对应子目录
- 知识库：`write_file` 到 `vault/` 对应分类目录

### Step 4：告知用户

一句话说明存到哪里 + 为什么存那里

## 六、运行时检索——11 步信息流（v3 升级）

> **v3 升级（2026-06-04）**：从 v1 老版 6 层升级到 11 步信息流

### 6.1 11 步信息流

用户提问时，按以下 **11 步逐层走完，命中即进入第 5 步工具决策**：

```
1. 指令
   ↓
2. Agent
   ↓
3. 大脑（方法论，Holographic fact_store）
   命中 → 进入第 5 步工具决策
   未命中 ↓
4. 图书馆 5 层（按顺序，不跳步）
   4.1 踩坑经验（vault/踩坑记录/）
   4.2 知识库（vault/entities/ → vault/）
   4.3 近期对话（session_search）
   4.4 缓存点（data/{模块}/cache/ mtime+TTL，根据需要及时更新数据）
   4.5 网络搜索（web_search）
   任意层命中 → 进入第 5 步工具决策
   ↓
5. 判断调用哪种工具（5 步全自动）
   5.1 扫描 available_skills → skill_view(name) 加载
   5.2 选对工具（分析→execute_code / 改配置→patch / 查源码→search_files / 网络→web_search / 搜索→fact_store / 文件→read_file）
   5.3 查可用性（注册≠激活，显式检查——踩坑：fact_feedback 从未被调用）
   5.4 批量优先（3+次同类调用→execute_code 合并）
   5.5 安全验证（破坏性操作先 --dry-run / backup / 确认）
   ↓
6. 处理数据/信息/咨询
   ↓
7. 结果/反馈
   ↓
8. 迭代/完善方法论（fact_store 存回大脑或图书馆）
```

### 6.2 第 0 层：指代词快速路径 🏃

> 第 0 层在 11 步中作为 4.3 步"近期对话"的快速版本

```python
if any(w in user_query for w in ["刚才", "之前", "上一条", "你刚才说", "刚刚"]):
    session_search(user_query)
    return
```

### 6.3 第 1 层：Holographic 双重检索 🧠

```
fact_store(query="关键词1 关键词2")
```

返回结果包含：`fact_id`, `content`, `trust_score`, `created_at`（跨 session，无隔离）。
→ 命中 → 进入第 5 步工具决策
→ 未命中 → 进入 4.1 踩坑经验

> ⚠️ **Holographic 的检索局限**：HRR 代数是符号匹配，不是语义理解。
> 存了"市场高估时不建仓"，搜"牛市该不该买"可能不命中。
> **建议存事实时使用广谱关键词**（见「HRR 关键词编码策略」章节），让 HRR 更容易匹配到。
>
> ⚠️ **FTS5 中文分词硬伤**：FTS5 默认 unicode61 tokenizer 不识别中文词语边界，纯中文长句（连续汉字无空格/英文/数字/标点）被当作一个 token。这让中文 `fact_store(query=...)` 检索可能返回空。
> **对策**：搜中文方法论时如果 `fact_store` 返回空，不硬试同义词，直接跳到 4.3 近期对话 `session_search` 兜底。
> **预防**：存新事实时，content 用短句 + 空格分隔关键词（如"高估 不建仓 等待 保守"），确保 FTS5 可索引。

### 6.4 第 2 层：缓存点检查（4.4 步）

```
检查 data/{模块}/cache/ 文件 mtime + TTL
→ 详见 cache-check skill
```

**v3 升级说明**：在 v1 老版中缓存点是第 2 层（早于知识库），在 v3 中移到 4.4 步（在知识库、近期对话之后）。

### 6.5 第 3 层：知识库（4.2 步 Vault + 实体页）

```
read_file entities/ → read_file vault/
```

**v3 升级说明**：在 v1 老版中知识库是第 3 层（晚于缓存点），在 v3 中移到 4.2 步（在踩坑经验之后、近期对话之前）。

### 6.6 第 4 层：近期对话（4.3 步）

```
session_search(关键词) — 换同义词再试
```

### 6.7 第 5 层：网络搜索（4.5 步）

```
web_search —— 最后手段
```

### 6.8 第 5 步：工具调用决策（v3 新增）

| 步骤 | 做什么 | 原因 |
|------|--------|------|
| 5.1 **扫描 skills** | 当前任务匹配哪个 skill？→ `skill_view(name)` 加载 | skill 封装了完整流程+陷阱，比手拼更稳 |
| 5.2 **选对工具** | 任务需要什么能力？分析→`execute_code` / 改配置→`patch` / 查源码→`search_files` / 网络→`web_search` / 搜索→`fact_store` / 文件→`read_file` | 见下方「工具选用速查」表 |
| 5.3 **查可用性** | 目标工具是否已注册？未注册→降级方案。**踩坑**：`fact_feedback` 注册了但从未被主动调用 | 注册≠激活，显式判断才能打破惯性 |
| 5.4 **批量优先** | 重复操作（3+次同类调用）→ `execute_code` 合并 | 减少 context 膨胀 + 原子回滚 |
| 5.5 **安全验证** | 破坏性操作先 `--dry-run` / backup / 确认 | 见「执行前验证」|

### 6.9 第 7-8 步：结果/反馈 + 迭代方法论（v3 新增）

```
6. 处理数据/信息/咨询
   ↓
7. 结果/反馈
   ↓
8. 迭代/完善方法论
   - 教训 → fact_store(source="lesson")
   - 方法论 → fact_store(source="general")
   - 完整文档 → vault/
   - 实体卡片 → vault/entities/
   - 完整踩坑经过 → vault/踩坑记录/ + fact_store(source="lesson") 索引行
```

### 6.10 11 条检索原则（v3 升级）

1. **指代词优先**：含指代词先查近期对话（4.3 步），不绕圈子
2. **记忆优先**：之前聊过的事先查 Holographic（第 3 步大脑），不瞎猜
3. **知识库优先**：踩坑（4.1）+ 知识库（4.2）覆盖大部分结构化信息
4. **近期对话次之**：第 4.3 步 `session_search` 兜底
5. **缓存点次之**：第 4.4 步 `data/cache`（根据需要及时更新数据）
6. **网络搜索兜底**：第 4.5 步 `web_search`（最后手段）
7. **工具决策强制**：第 5 步 5 步全走，**不**跳步
8. **批量优先**：3+次同类调用合并 `execute_code`
9. **安全验证**：破坏性操作先 --dry-run / backup / 确认
10. **结果反馈**：第 7 步必须显式给出结论
11. **诚实原则**：找不到就说找不到，不编造

## 七、Holographic 插件使用详解

### 配置（config.yaml）

```yaml
plugins:
  hermes-memory-store:                          # ← 注意：key 名是 hermes-memory-store
    db_path: {工作区}/memory_store.db
    auto_extract: 'false'                       # 依赖 SOUL.md 三问流程，不自提取
    default_trust: '0.5'                        # 新事实信任分（默认 0.5，中性推荐）
    min_trust_threshold: '0.3'                  # 检索过滤下限（默认 0.3）
    temporal_decay_half_life: '0'               # 关闭时间衰减（方法论不过期）
    hrr_weight: 0.15                            # HRR 检索权重（中文场景推荐 0.15）
    # hrr_dim: 1024  ← 默认值，无需显式设置
```

> ⚠️ **配置 key 注意**：Holographic 的配置键是 `plugins.hermes-memory-store`，
> 不是 `plugins.holographic`。这是 Hermes 内置插件系统的统一命名。
> 激活后，`fact_store` 和 `fact_feedback` 两个工具自动注册到工具列表。

### `fact_store` 工具

**用途**：存储事实 + 检索记忆

**存储模式**：
```json
{
  "action": "fact_store",
  "parameters": {
    "content": "市场全面高估时不建仓，等机会",
    "query": "建仓 高估 时机",
    "source": "投资原则"
  }
}
```

- `content`：要存的事实内容（必填）
- `query`：HRR probe 关键词，也用于后续检索匹配（建议填多个同义词）
- `source`：来源标签（可选，如"投资原则"、"系统运维"）

**检索模式**：
```json
{
  "action": "fact_store",
  "parameters": {
    "query": "高估 不建仓 保守"
  }
}
```

返回匹配的事实列表。

### `fact_feedback` 工具

**用途**：对检索结果进行反馈，校准信任分

```json
{
  "action": "fact_feedback",
  "parameters": {
    "fact_id": "xxx-xxx-xxx",
    "action": "helpful"
  }
}
```

- `action`: `helpful` / `unhelpful`

## 八、Holographic 配置调优

> Holographic 默认权重（FTS5=0.4, Jaccard=0.3, HRR=0.3）适合通用场景。
> 如果搜索效果不理想，可以在配置层面调整。

### 字段含义

| 字段 | 默认值 | 作用 | 对应运行时表现 |
|------|--------|------|---------------|
| `hrr_dim` | `1024` | HRR 向量维度 | `hrr_vector` 字段 BLOB 大小 = `hrr_dim × 8` |
| `hrr_weight` | `0.3` | HRR 检索权重 | score = FTS5×0.4 + Jaccard×0.3 + HRR×hrr_weight |
| `default_trust` | `0.5` | 新事实初始信任分 | 影响 trust 加权后的 final score |
| `min_trust_threshold` | `0.3` | 检索过滤下限 | trust < 0.3 的事实不参与召回 |
| `auto_extract` | `'false'` | 是否自动提取 fact | 关掉，靠 SOUL DIKW 三问手动分流 |
| `temporal_decay_half_life` | `0` | 时间衰减半衰期（天）| 0 = 不过期（方法论场景） |

### 调优指引

**场景 1：中文文档/精确查找**
→ 降低 `hrr_weight`（减小代数匹配的噪声）
```yaml
plugins:
  hermes-memory-store:
    hrr_weight: 0.15   # FTS5 + Jaccard 占主导
```

**场景 2：灵活近义搜索（口语化/模糊描述）**
→ 保持或提高 `hrr_weight`
```yaml
plugins:
  hermes-memory-store:
    hrr_weight: 0.4    # HRR 代数匹配占比更高
```

**场景 3：无 numpy 时自动降级**
如果 numpy 不可用，HRR 权重**自动归零**，并重新分配给 FTS5=0.6, Jaccard=0.4。

## 九、HRR 关键词编码策略

> ⚠️ 以下是最关键的优化点——**HRR 检索的成败 90% 取决于 query 参数的编码质量**。
> 编得好，HRR 效果接近语义搜索；编得差，存进去就找不回来了。

### 核心公式

```
query = 核心概念 + 同义词群 + 近义词群 + 相关场景词
```

### 好例子 vs 差例子

| | query 参数 | 效果 |
|--|-----------|------|
| ❌ | `"建仓"` | 用户只说"进场"就搜不到 |
| ✅ | `"建仓 买入 入场 加仓 进场 开仓 买进"` | 无论哪种说法都能命中 |
| ❌ | `"高估"` | 搜"估值过高 泡沫 贵了"都不中 |
| ✅ | `"高估 估值过高 泡沫 太贵 不便宜 高估值"` | 全面覆盖 |

### 分类编码模板

**投资原则类：**
```python
query = " ".join([
    # 核心概念
    "建仓 加仓 买入 入场",
    # 反面词（HRR 能识别反面关系）
    "不减仓 不卖出 持有",
    # 条件/场景
    "时机 等待 确认 信号 右侧 左侧",
    # 情绪/判断
    "保守 谨慎 观望 耐心",
])
```

**用户偏好类：**
```python
query = " ".join([
    "飞书 报告 推送 通知",
    "偏好 喜欢 习惯 方式",
    "接收 发送 格式 排版",
])
```

## 十二、踩坑经验（lesson）

> **结论→ `fact_store(source="lesson")`** | **完整经过→ `vault/踩坑记录/`**

### 12.1 反模式：把公开网络可查信息存进 Holographic 大脑

**症状**：验证完一条新闻/技术/产品信息后，把"X 是 Y 参数/规格/状态"这种公开信息 `fact_store` 进大脑。

**用户反馈**："这个存记忆里干嘛"

**根因**：
- Holographic 大脑只该存"个人专属/项目专属/高频调用/方法论"
- 公开网络信息（技术参数、新闻事件、产品发布）**不是**个人专属、不会高频调用、有时效性
- Google 一下就有 → 存进大脑 = 污染检索 + 占用 token

**修复（DIKW 四问前置）**：存 Holographic 之前问三个问题：

| 问题 | 三个 No → 不存 |
|------|----------------|
| 30 天后还会被调用吗？ | 公开新闻/规格：No |
| 会被调用 5+ 次吗？ | 一次性事件：No |
| 是只属于我们知道的吗？ | 公开技术报告：No |

**正确归档路径**：
- 公开新闻/规格 → **不存**（Google 就有）
- 个人偏好/操作原则/项目约定/踩坑教训 → **Holographic**

### 12.2 反模式：动态数据塞进 Hindsight（旧系统）

之前的版本把净值、动量、短期判断存到 Hindsight，导致：
- 过期数据污染（用户一问就从 Hindsight 翻出旧数据）
- 高频检索被低价值数据占满

**正确做法**：动态数据进 data cache，方法论进 Holographic

### 12.3 反模式：DIKW 被 bypass（"记住"走捷径调 memory）

**症状**：用户说"记住之前讨论的内容" → 模型直接调 `memory(action='add')` 倒数据

**根因**：
- `dikw-memory-flow` skill 触发条件写"用户说记住→强制执行"
- skill 的 frontmatter `triggers: []`（靠 SOUL 驱动）
- **SOUL.md 中没有对应的强制执行铁律**
- 模型在"简单指令"压力下走捷径，跳过归纳和三问判断

**修复**：必须在 SOUL.md 铁律中加入强制规则（"记住"类指令必须先走 DIKW 三问判断）

### 12.4 反模式：连续 CJK 文字被 FTS5 / LIKE 当做一个 token

**症状**：中文查询"左侧建仓策略"在 FTS5 和 LIKE 兜底中都不命中

**根因**：
- FTS5 的 unicode61 tokenizer 无法分割连续 CJK 字符
- `re.findall` 的 `[\u4e00-\u9fff]{2,}` 模式同样将连续汉字视为单个 token

**修复**：对 >4 字的 CJK token 拆 2-gram 滑窗
```python
if re.match(r"^[\u4e00-\u9fff]+$", t) and len(t) > 4:
    expanded.extend(t[i:i+2] for i in range(len(t) - 1))
```

**验证**：v2 升级后 6/6 中文查询命中 L1（之前 0 条）。

### 12.5 反模式：听到"信息流"直接跳到第 8 步

**症状**：主上问"信息流" → 跳过 1-7 步直接进入第 8 步"迭代方法论"开始分析

**根因**：
- "信息流"在主上语境中 = 完整 11 步运转路径
- "信息流"**不是** DIKW 4 层学术分类
- "信息流"**不是** 任何具体工具

**正确做法**：听到"信息流/检索/查找"类指令 → 严格按 1→2→3→4.1→4.2→4.3→4.4→4.5→5→6→7→8 走，**不**跳任何一步。
